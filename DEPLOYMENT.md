# Deploying Cycle Haven

The live demo runs on three free services. Total cost: nothing, permanently.

| Piece | Service | Why this one |
|---|---|---|
| Database | [Neon](https://neon.com) | Free plan does not expire. 0.5 GB storage, 100 compute-hours/month |
| API | [Render](https://render.com) | Free Docker web service, 750 instance-hours/month |
| Frontend | [Vercel](https://vercel.com) | Free static hosting on a CDN, no cold start |

> **Why not Render's database?** Render's free PostgreSQL **expires 30 days after
> creation**. A demo link deployed that way works for a month and then silently breaks —
> which is worse than not deploying it, because you will not notice. Neon's free plan has
> no expiry.

---

## 1. Database — Neon

1. Sign up at [neon.com](https://neon.com) and create a project named `cyclehaven`
2. On the dashboard, copy the **connection string**. It looks like:

```
postgresql://myuser:mypassword@ep-cool-name-123456.us-east-2.aws.neon.tech/neondb?sslmode=require
```

3. **Split it into three values** — Spring needs them separately, and the URL needs a
   `jdbc:` prefix. From the example above:

| Variable | Value |
|---|---|
| `DATABASE_URL` | `jdbc:postgresql://ep-cool-name-123456.us-east-2.aws.neon.tech/neondb?sslmode=require` |
| `DATABASE_USERNAME` | `myuser` |
| `DATABASE_PASSWORD` | `mypassword` |

Note what changed: `postgresql://` became `jdbc:postgresql://`, and the `user:password@`
part was removed from the URL. Keep `?sslmode=require` — Neon refuses unencrypted
connections.

## 2. API — Render

1. Sign up at [render.com](https://render.com) and connect your GitHub account
2. **New → Blueprint**, select the `Cycle-Website` repository
3. Render reads [`render.yaml`](./render.yaml) and prompts for the values marked
   `sync: false`. Fill in:

| Variable | Value |
|---|---|
| `DATABASE_URL` | from step 1 |
| `DATABASE_USERNAME` | from step 1 |
| `DATABASE_PASSWORD` | from step 1 |
| `CORS_ALLOWED_ORIGINS` | leave as `https://placeholder.vercel.app` for now — step 3 gives you the real value |
| `SEED_ADMIN_EMAIL` | your admin email |
| `SEED_ADMIN_PASSWORD` | **a strong password you choose** |

`JWT_SECRET` is generated by Render automatically and never appears in the repository.

4. Deploy. The first build takes 5–10 minutes (Maven downloads the world once).
5. Note the URL — `https://cyclehaven-api.onrender.com` or similar
6. Verify: open `https://<your-api>.onrender.com/actuator/health` → `{"status":"UP"}`

The catalogue seeds itself on first start, so the API comes up with all 17 products.

---

## 3. Frontend — Vercel

1. Sign up at [vercel.com](https://vercel.com), connect GitHub, **Add New → Project**,
   import `Cycle-Website`
2. **Root Directory: `frontend`** — this matters; the repository root has no
   `package.json` and the build will fail without it
3. Framework preset should auto-detect as **Vite**
4. Add an environment variable:

| Name | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://<your-api>.onrender.com` (no trailing slash) |

5. Deploy. Note the URL — `https://cycle-website.vercel.app` or similar

---

## 4. Close the loop

The API is still configured to reject your real frontend, because CORS was set to a
placeholder. Fix it:

1. Render → your service → **Environment**
2. Set `CORS_ALLOWED_ORIGINS` to your exact Vercel URL, e.g.
   `https://cycle-website.vercel.app`
3. Save — Render redeploys automatically

Open the Vercel URL. If products load, everything is wired correctly.

> **If the shop is empty and the browser console shows a CORS error**, the origin does not
> match exactly. It is case-sensitive, must include `https://`, and must have **no trailing
> slash**.

---

## 5. Keep it warm (optional, but do it)

Render spins a free service down after **15 minutes** without traffic, and waking it takes
about a minute. Someone opening your link from a resume sees a spinner for that whole
minute, which is a poor first impression.

Free fix — ping it on a schedule:

1. Sign up at [uptimerobot.com](https://uptimerobot.com)
2. **Add New Monitor** → HTTP(s)
3. URL: `https://<your-api>.onrender.com/actuator/health`
4. Interval: **10 minutes** (under the 15-minute idle threshold)

The arithmetic works out: a continuously-running service uses 744 hours in a 31-day month,
inside the 750-hour free allowance. You also get uptime monitoring and an email if the API
goes down.

---

## Updating the deployment

Both platforms watch the repository. `git push` to `main` triggers a rebuild of whichever
side changed. No manual deploy step.

---

## Costs, honestly

Everything above is free, permanently, at this scale. The limits you would hit first:

- **Neon**: 0.5 GB storage. Product images are database blobs, and the seeded catalogue is
  about 1.2 MB, so this is not close.
- **Neon**: 100 compute-hours/month. The database suspends after 5 minutes idle and
  resumes on demand, so a demo consumes very little.
- **Render**: 750 instance-hours/month — enough for exactly one always-on service.

If you later want the API to never sleep without the pinger, Render's Starter plan is the
upgrade; check [render.com/pricing](https://render.com/pricing) for the current figure.
